# ContentCreator: scope, prerequisites and restrictions

What ContentCreator supports, what it cannot do compared with SiteArchitect, and what a project
must have in place before editors can work in it. Read this before you promise an editor
workflow ("the editor can set it back to the default", "the editor can follow the link to the
remote project") or before you judge a template for ContentCreator.
Everything here is **[odfs]** — *Template development › ContentCreator › Restrictions /
Functional scope / Requirements* (FirstSpirit 2026.5; the Restrictions page is dated 2026-02).
These are the documented restrictions; they are not re-tested live **[verify]**. Field findings
that are **not** on those pages are in `does-not-work-in-contentcreator.md`.

## What an editor works with: supported components

ContentCreator supports these input components: `CMS_INPUT_CHECKBOX`, `CMS_INPUT_COMBOBOX`,
`CMS_INPUT_DATE`, `CMS_INPUT_DOM`, `CMS_INPUT_DOMTABLE`, `CMS_INPUT_IMAGEMAP`,
`CMS_INPUT_LINK`, `CMS_INPUT_LIST`, `CMS_INPUT_NUMBER`, `CMS_INPUT_PERMISSION`,
`CMS_INPUT_RADIOBUTTON`, `CMS_INPUT_TEXT`, `CMS_INPUT_TEXTAREA`, `CMS_INPUT_TOGGLE`,
`FS_BUTTON`, `FS_CATALOG`, `FS_DATASET`, `FS_INDEX`, `FS_REFERENCE`; and the design elements
`CMS_COMMENT`, `CMS_GROUP`, `CMS_LABEL`. [odfs]
A component that is not in this list is not offered as a supported component by the page. Whether
it still renders is not stated **[verify]**. Component semantics:
`firstspirit-templating-reference` (`references/gom/`).

## Component restrictions

| Component | Restriction in ContentCreator |
| --- | --- |
| `CMS_INPUT_DATE` | Manual input (`allowInput`) is not possible. The format symbols `w`, `W`, `D`, `F` are not supported. The names shown for `z`, `M`, `E` follow the **client language** set on the start page, not the content language. |
| `CMS_INPUT_DOM` | `maxCharacters` (length limit) has no effect. |
| `CMS_INPUT_DOMTABLE` | No cell formatting: format templates still work, cell-specific attributes do not. No cell merging. |
| `CMS_INPUT_IMAGEMAP` | Only rectangular border objects can be created. |
| `CMS_INPUT_PERMISSION` | Limited: validation scripts cannot be used. |
| `FS_CATALOG`, `FS_INDEX` | Navigation between neighbouring elements differs from SiteArchitect (different user guidance). |
| `FS_INDEX` | In the data-sources view a column of this type shows only if it uses the `DatasetDataAccessPlugin`. |
| `FS_DATASET` | `allowDelete` has no effect: the editor can only remove the reference, not delete the dataset. |
| `FS_REFERENCE` | `imagePreview` has no effect (a thumbnail is always shown). Unlike SiteArchitect, new pages can be created here, depending on the configuration. |
| `CMS_GROUP` | Grouped elements show only as tabs in the upper form area (never on the page or below); `height` and `scrollable` have no effect. |
| `CMS_LABEL` | `size`, `bold` and `italic` have no effect. |
| `CMS_COMMENT` | No restrictions. |

## General restrictions

- **Release-based projects only.** ContentCreator does not support auto-release projects
  (project property "Use release" switched off in the project's server configuration). [odfs]
- **Default values** work only to a very limited extent. The first time a form opens, the
  non-persistent default is shown; **saving the form stores it persistently**, and there is no
  way in ContentCreator to reset a saved value to its default or to switch the save off in
  advance. In SiteArchitect the default stays non-persistent until the editor accepts it. Plan
  forms accordingly: a default is effectively a pre-filled value. [odfs]
- **The preview page is the unit of action.** The editor sees page, page reference, referenced
  media and datasets as one unit. Actions that do not target a single element (element-state and
  workflow indicators, scripts and toolbar plug-ins from the "Actions" menu,
  `WebeditUiAgent`) act on the element that the preview page is based on: usually the page
  reference. For a page that outputs **exactly one dataset**, the dataset is used instead, so a
  workflow started from the page state acts on the dataset. With several datasets the page
  reference is used. [odfs]
- **Preview may be stale** after template changes; an editor can request a fresh preview
  manually. A page opened in a **new window** has no ContentCreator bar. Links into **remote
  projects** cannot be followed in the preview. [odfs]
- **Reference names cannot be typed**; they are generated by the system. [odfs]
- **Soft hyphens** can be typed into a ContentCreator form but are displayed only in
  SiteArchitect forms. [odfs]
- **Browsers** differ in some functions; ContentCreator works with any supported browser, but
  not every special function is available in all of them. [odfs]
- **Not available** (compared with SiteArchitect): import of MS Word documents (a separate
  module), project home page, manual version comments. **Also not available:** permission
  assignment; editing document groups (read access remains). [odfs]
- Rules and forms can be adjusted directly in ContentCreator with its **development tools**. [odfs]

## Stores in ContentCreator

- Global settings (project and user settings), the store restrictions and the template store
  are not displayed. [odfs]
- **Page store:** sections based on table templates (content projection) cannot be created;
  create them in SiteArchitect. [odfs]
- **Data store:** data sources and data-source folders cannot be created. Not every input
  component type is shown in the overview (column or list view), there is no filter and only
  limited sorting. Permissions assigned to data sources are not considered by the "Set filter"
  option, for technical reasons. [odfs]

## Prerequisites and project setup

Before editors can use ContentCreator, in the project (the documentation points to the
administrator manual for each):

| Topic | What to do |
| --- | --- |
| System and browser requirements | Check the technical requirements in the administrator documentation. |
| Configuration and settings | ContentCreator configuration and "ContentCreator settings" (project properties); a local project application only if a separate instance per project is needed. |
| Browser | Configure the browser for editing as described in the administrator documentation. |
| Template set | Templates must be written for the template set the administrator configured for ContentCreator: an existing one (the HTML channel) or a separate "ContentCreator" channel. Check the layout **with** control elements (standalone ContentCreator view) and **without** (SiteArchitect preview). |
| EasyEdit / InEdit | Adapt the templates (`editorId`): `editing-in-the-preview.md`. EasyEdit works only together with Content Highlighting, because both use the same markers in the templates. |
| Actions and buttons | `FS_BUTTON` handler classes, "Configure actions": `customising-contentcreator.md`. |
| Datasets | Editable in the data-sources area. The table is built from the **mapping** of the table template; a column can be hidden there (the "Display" option), which helps with large data volumes; default sorting comes from the database. To edit a dataset **directly in a preview page**, the table template needs "Use in ContentCreator" **on** and a **preview page** on its Properties tab; only then does "New" offer it. [odfs] |

The page "Requirements" itself is a table of pointers to those documents; it lists no
versions or numbers.

## What this means for a template review

Review a template for ContentCreator against the lists above, not against SiteArchitect
behaviour: length limits on `CMS_INPUT_DOM`, `allowInput` on dates, `allowDelete` on
`FS_DATASET`, `imagePreview`, cell formatting in DOM tables, and anything that relies on a
default value being reversible are all inert. The project-wide readiness checks are in
`downstream analysis/references/contentcreator-readiness-checks.md`.
